# DSM integration design

The source fork remains unchanged outside `synology/`. Runtime uses the official
`deluan/navidrome:0.64.2` image, pinned to its verified registry index. The
integration preserves Navidrome's UI; it does not introduce another login page.

## Identity and roles

DSM nginx serves HTTPS using the system default certificate. The SDK gateway
verifies DSM sessions (`dsm-users`, `app-privilege`). Ordinary accounts must
pass the current DSM App privilege check; administrators follow the SDK
administrator admission policy.
It overwrites `Remote-User`, `Remote-Uid`, and `Remote-Groups`. Header mode is
intentional: Navidrome has no native OIDC consumer. Navidrome requires an absolute logout
configuration URL at startup; the adapter replaces its fixed placeholder only
in generated HTML with a same-origin sign-out form. The form submits the
SDK-required POST to `/_sso/logout` using a same-origin fetch with manual
redirect handling, then navigates separately. This keeps the subsequent DSM
authorize redirect outside the form CSP restriction. A nonce-limited script
and visible retry button protect that flow. A GET cannot end a gateway session.

A small nonroot integration adapter supervises the unmodified executable in the
same official container. Navidrome binds only `127.0.0.1:4534`; its external auth
trust list is exactly `127.0.0.1/32`. Only the adapter reaches this listener.
The adapter binds the SDK's dedicated internal bridge address on port 4533,
accepts only the exact host bridge peer, and exposes no Docker published port.
Other containers and LAN clients have no published backend endpoint. The SDK
owns the sole public ingress. A host administrator, Docker administrator, or
local host process able to originate traffic from that bridge peer is within
the trusted NAS host boundary; this topology does not isolate hostile host
processes with the same network authority. Stronger local process isolation
would require an authenticated SDK-to-upstream transport.

Before opening adapter ingress, the supported upstream header flow creates a
reserved internal administrator (`__dsm_bridge_internal__`). Its upstream
autogenerated password is unknown to users. The adapter never accepts that
name from the gateway. Before each protected request, it uses the upstream
native API privately to provision the gateway-verified DSM identity with an explicit
`isAdmin` value. The first ordinary DSM user is created as an ordinary user.
The adapter synchronizes every protected request to the role asserted by the
gateway. SDK 0.22.0 retains that administrator bit in an existing `dsm-users`
session; DSM role changes take effect after fresh sign-in/session expiry
(15 minutes here). This is a published SDK limitation; the adapter does not
claim immediate detection of host group changes. An API failure prevents forwarding. No database schema is patched.

UID-to-upstream-ID bindings are stored in a private, atomically replaced file in
the persistent data volume. Renames retain the upstream ID. Unbound native name
collisions and case-insensitive collisions fail closed. Browser JWT headers,
cookies and the `jwt` query credential cannot override the DSM identity.
Account creation/deletion through the browser is managed by DSM; the owner can
still edit their own password and preferences in the upstream UI.

## Native clients and sharing

The released SDK already supports permanent segment-matched passthrough.
`/rest` and `/share` bypass DSM admission and retain the client's own upstream
credentials. The gateway strips its cookies and all configured identity headers
on those requests, including requests made with an existing gateway session.
The adapter strips these identity headers again. Navidrome validates Subsonic
tokens/passwords; its own share handler validates anonymous share URLs.

In Navidrome's personal settings, set a separate Navidrome password for native
Subsonic clients. Use the Navidrome username shown in that UI and the App's HTTPS
origin. The DSM password is never copied into Navidrome. DSM logout does not
revoke an independent native-client password or a public share link. Remove the
share or change the Navidrome password to revoke that native access.

## Account deletion

The manifest registers SDK `account.on_delete`. The package-owned native helper
reads only this package's generated gateway endpoint and private runtime secret;
it signs a bounded deletion request to the adapter. The public gateway cannot
invoke the control route: protected calls carry DSM identity, which control
requests reject, and passthrough paths cannot resolve to it. Control requests
also require a valid HMAC and a timestamp within 30 seconds. Deletion is
idempotent and uses the upstream user API, removing the binding only after
success. SDK pending actions retry while the container is unavailable. Local
DSM account deletion uses the SDK watcher; missing directory users require the
SDK's explicit administrator purge policy. No DSM users are modified.

## Storage and lifecycle

The install wizard selects one existing DSM Shared Folder. SDK permission
handling grants the fixed package account read-only access and mounts it at
`/music`. Every admitted music user sees the library authorized for the package;
this is not per-user DSM file ACL delegation. The container runs with the fixed
package UID/GID, drops capabilities through the SDK, uses a read-only rootfs,
and has only a private data volume plus a bounded executable temporary mount.
The packaged adapter is reconstructed from bounded 60 KiB arguments into that
private mount. A 32 MiB stack resource limit permits the combined immutable
payload to pass Linux exec limits; no network download or writable image is
used. Device acceptance must verify Container Manager preserves this limit.
SDK nonroot storage initialization creates `/var/tmp/navidrome` without chown.

The adapter handles TERM/INT, terminates and reaps its child, and stops if the
upstream process exits. Restart and upgrades retain the database, bindings,
passwords, playlists and shares. The packaging version is `0.64.2-0002` (upstream
version plus four-digit build); same-version packaging upgrades increment it.

SDK 0.22.0 retains Docker named data volumes even on uninstall's delete-data
choice and reports `COMPOSE_DATA_RETAINED`. It does not promise complete data
removal. Keep/delete acceptance must verify and record that actual behavior;
manual fixture-volume cleanup is a separate administrator operation.

## Released 0.22.0 candidate acceptance

The production `0.64.2-0002` SPK uses published CLI/templates/SDK/App 0.22.0,
UI 0.12.5 and executor/v0.20.0, without source overrides or Go replace.
Check/build/inspect passed with no findings; the adapter proof verifier and
source/expanded-SPK public scans passed.

A fresh DSM 7.3.2 x86_64 native installation selected a disposable music
Shared Folder. The package identity could read the test WAV and could not
write the file or its folder. Native start and DSM main-menu login reached
the unmodified upstream library. A five-second WAV played through the upstream
Songs page: the HTML audio clock advanced from 0.265 seconds to 5 seconds,
ended normally, and reported no media error.

Native stop/start returned the package to running state. Delete-data uninstall
displayed COMPOSE_DATA_RETAINED. After package and containers were absent, only
the disposable acceptance volumes, music share and upload were removed
separately; DSM package identity was retained.
